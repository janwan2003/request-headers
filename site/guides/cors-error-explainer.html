CORS error explainer: paste the console error, get the cause and the fix

Paste the CORS message from the browser console: has been blocked by CORS policy (Chrome and Edge), Cross-Origin Request Blocked (Firefox), or is not allowed by Access-Control-Allow-Origin (Safari). The page says what failed, whether your request reached the server, and whether response headers can fix it. Then it writes the headers the API must send, as plain headers or Express, nginx or Apache config, and a HeaderDial profile to try the fix in your own browser before you change the server. Everything runs in this page: it makes no network requests after it has loaded, and nothing you paste is sent anywhere.

      How to read a CORS error
      

      The error your code catches says nothing useful on purpose: Chrome throws TypeError: Failed to fetch, Firefox TypeError: NetworkError when attempting to fetch resource., Safari TypeError: Load failed, and Axios AxiosError: Network Error. The reason is in a separate console line:
      

        

      • Chrome and Edge: Access to fetch at 'URL' from origin 'your origin' has been blocked by CORS policy: reason. fetch becomes XMLHttpRequest, script or font for other request kinds. Response to preflight request doesn't pass access control check: before the reason means the OPTIONS preflight failed and the real request was never sent.
        • 

      • Firefox: Cross-Origin Request Blocked: The Same Origin Policy disallows reading the remote resource at URL. (Reason: reason). Status code: N. It does not name your origin. A failed preflight usually adds a second line, (Reason: CORS request did not succeed). Status code: (null).; the first line is the one that matters. The Network panel shows a short label such as CORS Missing Allow Origin.
        • 

      • Safari: Origin your origin is not allowed by Access-Control-Allow-Origin. Status code: N, followed by Fetch API cannot load URL due to access control checks.
        •

      When headers cannot fix it
      

        

      • The preflight gets an error status. A preflight needs a 2xx answer. A server with no OPTIONS route answers 404 or 405; one whose auth middleware runs before CORS answers 401, because the browser never sends your Authorization header with a preflight. Enable your framework's CORS middleware before auth, or answer OPTIONS with 204. In our tests in Chrome 159 and Firefox 158, adding every CORS header to a 404 preflight still failed (details), because a header rule cannot change a status code.
        • 

      • The preflight is redirected. Often http to https, or /items to /items/. Call the URL the redirect points to. A redirect of the request itself is no better: after a redirect to another origin the browser sends Origin: null, so in our tests a target that named the page's origin failed in both browsers, and only * on both hops worked.
        • 

      • A file:// page. Serve the folder over http: python3 -m http.server 8000 or npx serve, then open http://localhost:8000.
        • 

      • While developing, use a proxy. If you cannot change the API yet, let your dev server forward the calls. The browser then sees a same-origin request and sends no preflight. In Vite: server.proxy: { '/api': { target: 'https://api.example.com', changeOrigin: true } }, and call /api/… from your code.
        • 

      


      Why mode: 'no-cors' is not the fix
      

      Chrome's message ends with If an opaque response serves your needs, set the request's mode to 'no-cors'. With no-cors the request is sent, but your code gets an opaque response: status 0, no body, no headers, and it cannot send custom headers or a JSON Content-Type. It is for fire-and-forget requests and some images or scripts, not for reading an API.
      


      Why test the fix in the browser first
      

      CORS fixes often need two or three rounds: the origin first, then a header the preflight did not allow, then credentials. Each round on the server is a deploy. A HeaderDial profile adds the same response headers in your own browser, so you can paste each new error here, update the profile, and deploy once the request works. It needs site access to both the API host and the page's host, because the browser checks the response for the page that made the request. Give the profile an expiry (15 min to 1 day on each row) so it does not outlive the test. More on this in fix a CORS error while testing and CORS headers for local development.
      


      How the page works
      

      It matches the pasted text against the CORS messages Chrome, Edge, Firefox and Safari log in English, and reads the URL, the page origin (Chrome and Safari name it; Firefox does not) and any method or header name. The headers it suggests: Access-Control-Allow-Origin set to your page's origin (or * when the origin is unknown and no cookies are sent), Access-Control-Allow-Credentials: true when cookies are sent, and for a preflighted request Access-Control-Allow-Methods with the usual methods and Access-Control-Allow-Headers with Authorization, Content-Type and any header the error named. With a named origin the server should also send Vary: Origin, so caches keep one answer per origin. It is not in the browser profile, which only changes your own responses. Our end-to-end test feeds Chrome's real console errors into this page's code and applies the profile it builds until a credentialed PUT with a custom header works.
