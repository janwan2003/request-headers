How to modify headers in only one tab

To change headers in one tab only, open that tab, click the HeaderDial icon, and tick Only in this tab (until it closes) under Where it applies. The profile's headers then go on every request that tab makes, on any site it visits. Other tabs are left alone, even on the same URL, and so are new tabs and popups the tab opens. When you close the tab, HeaderDial switches the profile off. This is useful when you want two tabs side by side, one with a header and one without. Examples: a feature flag on and off, a logged-out view next to a logged-in one, or two Accept-Language values.

Steps

  1. Go to the tab you want to change and load the site.
  2. Click the HeaderDial icon in the toolbar while that tab is in front. Use the toolbar popup, not the full-tab editor: in the editor the checkbox is greyed out, because the editor tab is the only tab it knows about. If the site-access banner appears, choose Allow on all sites or Only <current host>.
  3. Add the headers to a profile. The tab setting belongs to the whole profile, so click + next to the profile chips for a new one if your other profiles should keep working everywhere.
  4. Open Where it applies and tick Only in this tab (until it closes). The label changes to "Only in one tab: page title (this tab)", the heading reads Where it applies (1 filter), and the profile chip gets a ⧉ mark. Ticking it also switches the profile on.
  5. Reload the tab.

Everything in the profile is limited to the tab: request and response headers, cookie rows and URL redirects. Other filters still apply on top. With + Only on… staging.example.com as well, the headers go only on that host's requests, and only from that tab.

What it covers, measured

We tested in November 2026 with HeaderDial 0.5.0 in Chrome for Testing 159.0.8154.6 and Firefox 158.0.1 on Linux. A profile with one request header, X-Tab: 1, was bound to one tab, and a local server logged whether each request carried it. In Chrome we ticked the box in the real toolbar popup. In Firefox we set the same profile through the extension's storage, because a test cannot open Firefox's toolbar popup.

The browser identifies a tab by a number, not by its address. That is why the header follows the tab to another site, and why a new tab or window opened from it does not get it, even when it is on the same site.

When the tab closes

In both browsers, closing the tab switched the profile off within a second. Its switch read Off, the checkbox went back to Only in this tab (until it closes), unticked, and no rule was left in the browser. In Chrome we also saw the ⧉ mark disappear. The headers stay in the profile, so to use them again, open the popup on another tab and tick the box again.

Tab numbers are not kept across a browser restart, so HeaderDial also switches tab-bound profiles off when the browser starts. We read this from the code but did not test a real restart.

Pitfalls

  • Sign-in and payment popups don't carry it. If your flow opens a popup or a new tab, the header is missing there. Use an + Only on… domain filter without the tab setting instead.
  • Service workers. Requests a site's service worker makes on its own have no tab, so a tab-bound profile misses them (measured in Chrome). If some requests lack the header on a site with a service worker, unregister the worker while testing, or use a domain filter.
  • Cookies are still shared. Removing Cookie in one tab gives a logged-out view there, but any Set-Cookie that tab receives still changes the cookies for every tab.
  • Back and forward may not send a request. In our Chrome test, going back showed a cached copy of the page, so no request reached the server. Reload when you check whether the header was sent.
  • Duplicating the tab makes a new tab. It is not covered, as the table shows.
