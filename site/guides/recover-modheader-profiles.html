Recover ModHeader profiles from a disabled extension

If ModHeader still appears on chrome://extensions or edge://extensions, even switched off with a warning, its profiles are most likely still on your disk. Choose its data folder below. This page reads the folder in your browser and gives you a JSON file in ModHeader's export format, which HeaderDial imports in one step. Nothing is uploaded: the page has no server and makes no requests with your files.

Don't click Remove on ModHeader yet. Removing an extension deletes its stored data. We checked this in Chromium 159: an extension's Local Extension Settings folder disappeared the moment it was uninstalled. Recover your profiles first, then remove it.

Where ModHeader keeps its profiles

Chrome and Edge keep each extension's chrome.storage data in a folder named after the extension's id, inside your browser profile:

  1. Open chrome://version (Chrome) or edge://version (Edge) and copy the Profile Path. It ends in Default, or in Profile 1, Profile 2 and so on if you use several browser profiles.
  2. Inside it, open Local Extension Settings, then the folder for ModHeader:

Nothing found there? Also try Sync Extension Settings/<id>, which holds data an extension saved to the browser's sync storage, and Local Storage/leveldb, where older extensions kept data in localStorage. This page reads all three folder types and only reports values that look like ModHeader profiles.

The browser writes to these files while it runs. If the page reports a damaged file, close the browser (or copy the folder elsewhere) and choose it again.

What you get

For each set of profiles found, the page lists every profile with its number of request headers, response headers and URL filters. Download .json saves the profiles in ModHeader's own export format, and Copy JSON puts the same text on the clipboard. In HeaderDial, click Import… in the footer and paste the text or choose the file. Headers, response headers, cookies, URL replacements, URL filters and resource types carry over. Tab, tab-group and window filters can't: their ids change every time the browser starts. The import guide has the full mapping.

If a key was saved several times, LevelDB keeps old copies until it tidies up its files. The page uses the newest copy of each key and ignores deleted keys, so you get the profiles as ModHeader last saved them.

Your profiles probably hold access tokens. The JSON file has them in plain text, so delete it after importing. The public reports on ModHeader say there is no evidence that it sent real users' data. A staging token that sat in a pulled extension is still cheap to rotate.

How this was tested, and what it does not cover

We do not have ModHeader's own data to test against, and we did not take its code apart to learn its storage format. Instead the reader looks for anything shaped like a ModHeader profile (a title with headers, respHeaders, appendMode and so on), wherever it is stored. We tested it on folders written by Chromium 159 (Chrome for Testing 159.0.8154.6). A test extension saved ModHeader-format profiles through chrome.storage.local and localStorage and overwrote them after a restart. That left an older copy in a compressed .ldb table and a 900-header profile spread across several log blocks. The page returned the newest profiles in each case. The test files and the reader are in the repository (extension/lib/leveldb.js, test/leveldb.test.js).

  • Not covered: Firefox. Firefox keeps extension data in an SQLite/IndexedDB database, a different format. If ModHeader still runs in your Firefox, use its own export instead.
  • Not covered: an extension you already removed. Uninstalling deletes the folder, and browser sync does not keep chrome.storage.local data. A backup of your profile folder from before the removal (Time Machine, File History, a disk image) still works: choose the folder inside the backup.
  • Not tested: Edge itself and real ModHeader data. Edge uses Chromium's storage code, so the format should be the same.
