Why was my cookie blocked? Paste the warning, get the fix

Paste the cookie warning from Chrome or Edge DevTools (This attempt to set a cookie via a Set-Cookie header was blocked because…) or from the Firefox console (Cookie “sid” rejected because…), the Set-Cookie line from the response headers, or both. Add the page's URL and the API's URL and the page also checks the line itself: same site or not, SameSite, Secure, Domain, Path, prefixes and size. You get the cause, the corrected Set-Cookie line, code for Express, PHP, Django or nginx, and a HeaderDial profile to try the fix in your own browser. Everything runs in this page: it makes no network requests after it has loaded, and nothing you paste is sent anywhere.

      Your own sites only. SameSite, Secure and third-party blocking protect users from cross-site tracking and request forgery. Loosen them only for cookies your app needs across sites, and keep HttpOnly on session cookies. The browser profile is for testing; it changes responses in your browser alone.
      


      Where to find the message
      

        

      • Chrome and Edge: the console says nothing about cookies (none of our 15 test cases logged a line there). Open DevTools, Network, click the request that sets the cookie, then the Cookies tab. A refused cookie is highlighted under Response cookies; hover the ⓘ or the row for the reason and copy it. For cookies that were stored but not sent, tick show filtered out request cookies under Request cookies. The Issues panel shows a headline for only some causes: in our tests just one, Mark cross-site cookies as Secure to allow setting them in cross-site contexts for SameSite=None without Secure.
        • 

      • Firefox: the Console logs one line per refused cookie when it is set, starting Cookie “name”. When a stored cookie is not sent (SameSite on a cross-site request), it logs nothing. Network → the request → Cookies shows what was sent and received.
        • 

      • Safari: it logs no reason. Web Inspector → Storage → Cookies shows whether the cookie was stored. Safari blocks all third-party cookies, so a cookie set by another site than the page is refused there even with SameSite=None; Secure.
        • 

      • The Set-Cookie line: Network → the request → Headers → Response Headers, or curl -si https://api.example.com/login | grep -i set-cookie.
        • 

      


      Same site or not? The rule behind most cookie problems
      

      SameSite is about sites, not origins. A site is the scheme plus the registrable domain (the part you buy: example.com, example.co.uk). Ports and subdomains do not matter.
      

      

      PageCookie URLSame site?
      

      http://localhost:5173http://localhost:8080Yes: ports do not count
      

      https://app.example.comhttps://api.example.comYes (but a different origin, so fetch still needs credentials: 'include')
      

      http://localhost:3000http://127.0.0.1:8000No: different hosts
      

      https://shop.vercel.apphttps://shop-api.vercel.appNo: vercel.app is a public suffix, like netlify.app, herokuapp.com, github.io, pages.dev and onrender.com
      

      http://localhost:5173https://api.example.comNo, and the cookie is third-party
      

      http://example.comhttps://example.comNo in Chrome and Edge (they compare schemes too)
      

      

      When the page and the API are different sites, the cookie needs SameSite=None; Secure, which needs https on the API. Firefox 158 is more lenient here than Chrome: it stores a cross-site cookie without SameSite (in a separate jar per top-level site), so code that works in Firefox can still fail in Chrome. The simplest fix is often to make them the same site: serve the API under the app's domain (api.example.com next to app.example.com), or call it through the dev server's proxy (Vite server.proxy, Next.js rewrites) so the browser only ever sees the page's own origin.

      When nothing is logged at all
      

        

      • The fetch does not include credentials. A request to another origin sends no cookies and ignores Set-Cookie unless you write fetch(url, { credentials: 'include' }) (axios: withCredentials: true). The API must answer with Access-Control-Allow-Credentials: true and your exact origin; the CORS error explainer covers those errors.
        • 

      • The Path is too narrow. Without Path, a cookie set by /api/auth/login is only sent to /api/auth/…. Chrome lists it as filtered out on the other requests; Firefox says nothing.
        • 

      • It is HttpOnly. document.cookie does not show it, but it is sent. Check the request's Cookie header instead.
        • 

      • It was deleted. Max-Age=0 or a past Expires removes the cookie; a logout route often does this.
        • 

      


      Why test the fix in the browser first
      

      Cookie fixes are deploy-and-retry work: change the attributes, deploy, log in again, look in DevTools. A HeaderDial profile adds the corrected Set-Cookie line to the API's responses in your own browser, so you can check that the rest of the flow works (the cookie is stored, then sent, and the API accepts it) before you change the server. A Send row goes further and adds name=value to requests directly, which tells you whether the backend works once the cookie arrives. The profile needs site access to the API's host. Its Set-Cookie line follows the same rules as the server's: SameSite=None; Secure still needs https. More in send a cookie with requests and test with Cookie and Set-Cookie headers.
      


      How the page works
      

      It matches the pasted text against the cookie messages Chrome, Edge and Firefox show in English and reads the cookie name where the message has one (Firefox's always do; Chrome's tooltips do not). Set-Cookie lines are parsed and checked against the URLs you enter: the site of each (with a built-in list of common public suffixes such as co.uk and vercel.app, not the full Public Suffix List), whether the cookie URL is https or localhost, whether Domain covers the host, and the default path. The corrected line keeps your attributes and changes only what the causes need.
