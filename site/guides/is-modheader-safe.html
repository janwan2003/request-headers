Is ModHeader safe? What was found, and how to check a header extension yourself

In July 2026 Microsoft and Google removed ModHeader from their extension stores. Researchers had found a browsing-history collector inside the genuine store version. The collector was switched off, and the published reports found no evidence that it collected or sent anyone's browsing data. But it was complete, and an ordinary update could have switched it on, so all three reports below advise removing the extension. If you still have it: recover your profiles first if you need them, then remove it, and replace any secrets you typed into it. This page summarises the reports as of 20 November 2026. It then shows how to check any header extension yourself.

What was reported

Three reports from July 2026, each linked where it is used: The Hacker News (13 July), Cybernews (15 July, updated 21 July) and VPN Central (16 July). All three describe the same analysis, by researchers at Stripe OLT.

  • Removed from both stores. Microsoft took down the Edge Add-ons listing on 3 July 2026 and Google the Chrome Web Store listing on 10 July (The Hacker News, VPN Central). On 20 November 2026 the Chrome Web Store address for ModHeader's extension ID, idgpnmonknjnojddfkpgkljpfnnfcklj, still showed no listing (we checked).
  • It was the real extension. The researchers analysed Chrome version 7.0.18. They matched its code against the Chrome Web Store's own signature data, so the code came from the official package and not from a fake copy. The Chrome listing had about 900,000 users, and third-party estimates add about 700,000 on Edge (The Hacker News, VPN Central).
  • What the hidden code was built to do. The background script still edited headers as normal. Mixed in with that code was a second system. It creates a device identifier, takes the domain of each page you open, encrypts it with a key built into the extension, and keeps up to 1,000 domains locally. About once a day it would upload them to an outside server and clear the local copy (The Hacker News, Cybernews, VPN Central).
  • Why it was dormant. Collection only ran if the browser matched an internal allow-list, and that list was empty in version 7.0.18. The check always failed, so no domain was recorded (The Hacker News, VPN Central). Cybernews quotes the researchers as saying they did not observe browsing history leaving the browser in that build (Cybernews).
  • What did run. On install, update and uninstall, the extension reported its name, version and browser to a second domain. It had also stored real request details on the local disk (The Hacker News, VPN Central). VPN Central notes that this local record does not prove that headers or credentials were sent anywhere.
  • Why it matters anyway. Turning the collector on needed only an update that filled the allow-list, with no new permission and no prompt. Automated scanners had rated the extension low risk (The Hacker News, Cybernews).
  • The developer. The Hacker News reported that the developer had not responded publicly as of its publication on 13 July. We have not checked for a later statement.

For network teams, the reports name the two domains involved, api.stanfordstudies[.]com (no link to Stanford University, per both reports) and extensions-hub[.]com, and suggest searching DNS and proxy logs for them (The Hacker News, VPN Central).

What to do if you used ModHeader

  1. Keep your profiles if you need them. Removing an extension deletes its stored data. If you never exported your profiles, recover them from ModHeader's data folder first. That page runs locally and uploads nothing.
  2. Remove it from every Chrome and Edge profile you use. Check that browser sync, or an extension policy on a work machine, does not install it again (The Hacker News, VPN Central).
  3. Replace secrets you put in it. If your profiles held API keys, bearer tokens or session cookies, revoke and reissue them. The reports say the extension's header history stored full headers on disk (The Hacker News, VPN Central).
  4. Import your profiles into another tool. HeaderDial reads ModHeader exports and the recovered JSON. See import your ModHeader profiles for what carries over.

Whatever you install next, check it with the steps below. For HeaderDial, here is what you will find:

  • Permissions: declarativeNetRequest, storage, alarms and activeTab. Access to sites is optional. It is not granted at install, and you grant it from the popup for all sites or for the current site only.
  • No webRequest, no content scripts, no tabs or history permission.
  • The extension's code makes no network requests, and there are no analytics and no account.
  • The source is public under the MIT licence on GitHub, so you can check all of the above.

On chrome://extensions in Chrome 159, HeaderDial's details page lists one permission, "Block content on any page", which is how Chrome describes declarativeNetRequest.

How to check any header-editing extension yourself

We checked the labels below in Chrome for Testing 159.0.8154.6 and Firefox 158.0.1 in November 2026. Other versions may word them differently.

1. Read its permissions

Open chrome://extensions (in Edge, edge://extensions) and click Details on the extension. Look at two parts of that page:

  • Permissions lists what the extension asked for, in plain words. "Block content on any page" is declarativeNetRequest. "Read and change your browsing history on all your signed-in devices" appeared for a test extension that asked for history and tabs. A header editor does not need that.
  • Site access shows whether it can reach the pages you visit. If it reads "Allow this extension to read and change all your data on websites you visit", with the options On click, On specific sites and On all sites, the extension asked for every site at install. Choose On specific sites and add only the hosts you test.

In Firefox, open about:addons, click the extension and open its Permissions and data tab. It lists required and optional permissions.

2. declarativeNetRequest or webRequest?

Both let an extension work with requests, in different ways:

The extension usesWhat its code sees
declarativeNetRequestIt gives the browser a list of rules, such as "set this header on requests to example.com", and the browser applies them. The extension's code is not told which pages you open or what the requests contain.
webRequest plus access to all sitesIts code is called for requests to every site, with the URL and headers. Some tools have good reasons for this. But that code then sees your traffic, so what it does with it matters more.

The details page does not always tell these apart. A test extension with webRequest and access to all sites showed no separate line for webRequest in Chrome 159; only the Site access text appeared. To be sure, read the extension's manifest.json: in its public source, or in the Extensions folder of your browser profile (chrome://version shows the profile path). Content scripts that match <all_urls> also mean its code runs inside every page.

3. Watch its own network requests

In Chrome or Edge:

  1. On chrome://extensions, turn on Developer mode. Each extension card now shows its ID and an Inspect views line.
  2. Click service worker next to Inspect views. This should open DevTools for the extension's background script.
  3. In that DevTools window, open the Network panel and use the extension as normal. Requests the background script makes are listed there while the window stays open.

In Firefox, open about:debugging, choose This Firefox, and click Inspect on the extension's entry. This should open developer tools for the extension; use the Network panel there in the same way.

None of these checks proves that an extension is safe. ModHeader's collector was switched off, so its Network tab would have shown no browsing data being sent. What the checks show is how much an extension could see. That is how much you are trusting its next update.

4. Other signs worth a look

  • Public source with readable recent history, so others can see what changed between versions.
  • Who publishes it. A change of owner, or a new business model such as ads, is a reason to look again.
  • No account and no analytics for a tool that runs entirely in your browser.
